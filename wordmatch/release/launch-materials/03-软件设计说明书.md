### 1.2 项目背景

当前英语词汇学习市场存在以下痛点：

1. **传统背词方式枯燥低效**：以列表翻页、反复抄写为主的记忆方式缺乏趣味性，用户难以坚持，学习中断率高达70%以上。
2. **缺乏科学复习机制**：多数背词应用仅提供简单的"认识/不认识"二分判定，未遵循艾宾浩斯遗忘曲线进行间隔重复，导致短期记忆无法转化为长期记忆。
3. **游戏化与学习割裂**：市面上的英语游戏应用往往"游戏性有余、学习性不足"，用户在游戏中获得的词汇记忆深度不够，无法形成有效的知识留存。

"单词消消乐"正是针对上述痛点而设计。本产品面向高中生及大学生群体，定位为"游戏化+AI+间隔重复"高效背词APP，旨在通过消除玩法的即时多巴胺反馈激发学习动力，借助SM-2科学记忆算法确保长期记忆效果，并利用AI大模型提供深度助学能力，实现"寓教于乐、科学记忆、智能辅助"三位一体的词汇学习体验。

### 1.3 软件概述

**产品定位**：单词消消乐是一款以英汉匹配消除为核心玩法的词汇学习应用，将经典消除游戏的即时满足感与科学记忆算法的长期有效性深度融合，打造"越玩越记得住"的学习体验。

**核心壁垒**：

1. **消除玩法的即时多巴胺反馈**：将英汉配对融入消除游戏机制，每次成功匹配即产生粒子特效、音效反馈和连击奖励，使学习过程产生强烈的正向情绪反馈，大幅提升用户的学习坚持率和每日活跃时长。
2. **SM-2科学记忆算法**：采用经过30年验证的SuperMemo SM-2间隔重复算法，根据用户每次匹配的表现（正确率、响应时间）动态调整复习间隔，确保每个单词在最佳遗忘临界点被复习，实现从短期记忆到长期记忆的高效转化。
3. **AI大模型深度助学**：集成大语言模型API，提供智能词库清洗、语境例句生成、词根词缀解析等深度助学功能，将单纯的"背词"升级为"理解式学习"。

**技术架构概览**：本软件基于Flutter 3.x跨平台框架开发，采用Dart语言编写，使用drift（原moor）作为SQLite ORM层实现本地数据持久化，采用Riverpod作为状态管理方案，实现响应式的数据流和高效的UI更新。

## 3. 功能模块详细说明

### 3.1 核心消除玩法模块

核心消除玩法是本软件最具特色的功能模块，将英汉词汇匹配与经典消除游戏机制深度融合，实现"边玩边记"的学习体验。

#### 3.1.1 网格规格

系统根据学习场景提供两种网格规格：

| 规格 | 网格大小 | 配对数量 | 适用场景 | 单词来源 |
|------|---------|---------|---------|---------|
| 小网格 | 4×4 | 8对（16张卡牌） | 新词巩固 | 当日新学单词 |
| 大网格 | 6×6 | 18对（36张卡牌） | 复习强化 | SM-2筛选的待复习单词 |

4×4网格适合新词场景，单词数量少但每词曝光频次高，有利于初记巩固；6×6网格适合复习场景，单词数量多但均为已学单词，重点在于间隔重复激活记忆。

#### 3.1.2 卡牌设计

每张卡牌包含以下视觉元素：

**正面（翻开状态）**：
- **英文卡牌**：居中显示英文单词（主字号24sp，粗体），左上角显示音标（phonetic_us，字号12sp，灰色），右上角显示发音图标（喇叭图标，点击触发TTS朗读）
- **中文卡牌**：居中显示中文释义（主字号22sp，中等粗细），释义内容为词库中的definition字段值

**背面（未翻开状态）**：
- 统一的装饰性UI设计，显示应用Logo或主题相关图案
- 背面颜色随当前主题变化（学术主题为深蓝色、森林主题为深绿色、太空主题为星空紫）

卡牌翻转动画采用3D透视变换（Perspective Transform），翻转时长300ms，配合缓动曲线（Curves.easeInOut），营造流畅的翻牌体验。

#### 3.1.3 匹配规则

匹配规则是消除玩法的核心逻辑，具体流程如下：

1. **选择阶段**：用户点击第一张卡牌（卡牌A），卡牌翻开并高亮显示；用户点击第二张卡牌（卡牌B），卡牌翻开。
2. **语义匹配判定**：系统检查卡牌A和卡牌B是否为同一单词的英文-中文配对。若卡牌A为英文、卡牌B为中文（或反之），且两者对应的word_id相同，则判定匹配成功。
3. **匹配成功**：两张卡牌执行消除动画（缩放+透明度渐变，时长500ms），从网格中移除，触发成功反馈。
4. **匹配失败**：两张卡牌保持翻开状态1秒后自动翻回背面，触发失败反馈。
5. **同侧匹配**：若用户选择的两张卡牌同为英文或同为中文，系统判定为无效选择，第二张卡牌不翻开并给出轻微抖动提示。

[截图：匹配成功瞬间，两张卡牌正在执行消除动画，周围出现粒子特效]

#### 3.1.4 防死局算法

为确保游戏始终可进行，系统内置防死局检测机制：

1. **路径校验**：每次消除一对卡牌后，系统遍历剩余所有卡牌对，检查是否存在至少一对可消除的英汉配对。若不存在，则触发"洗牌"操作。
2. **洗牌机制**：保留卡牌的已翻开状态不变，仅对未翻开的卡牌位置进行随机重排，确保重排后至少存在一条可消除路径。
3. **自动提示**：当用户连续3次匹配失败时，系统自动高亮一对可匹配的卡牌（边框闪烁3秒），引导用户找到正确配对，降低挫败感。

防死局算法的时间复杂度为O(n²)，其中n为剩余卡牌数量，在6×6网格（最多36张卡牌）下性能开销可忽略不计。

#### 3.1.5 动态难度调节

系统根据用户的实时表现动态调整游戏难度，实现自适应学习体验：

| 用户表现 | 难度调整 | 具体策略 |
|---------|---------|---------|
| 正确率 > 90% | 增加难度 | 在网格中混入1-2对干扰项（形近词或义近词），如"adapt/adopt"同时出现 |
| 正确率 60%-90% | 维持当前难度 | 不做调整 |
| 正确率 < 60% | 降低难度 | 移除干扰项，仅保留明确配对；延长卡牌翻开后的展示时间 |

难度调整在每个游戏对局开始时根据上一局的表现数据计算，对局中途不调整，避免干扰游戏体验。

#### 3.1.6 匹配反馈系统

反馈系统是消除玩法"即时多巴胺"体验的关键实现，分为成功反馈和失败反馈两类：

**成功反馈**：
- **视觉反馈**：消除位置播放粒子爆炸特效（50个粒子，随机方向散射，颜色随主题变化），持续800ms
- **听觉反馈**：播放清脆的"叮"音效，音调随Combo数递增（C4→D4→E4→F4→G4，五度循环）
- **语音反馈**：自动播放匹配单词的英文发音（TTS），帮助用户在消除瞬间强化听觉记忆
- **文字反馈**：屏幕中央短暂显示"Great!"/"Excellent!"/"Perfect!"等鼓励文字，文字大小随Combo数增大

**失败反馈**：
- **视觉反馈**：卡牌执行水平抖动动画（左右偏移8px，频率20Hz，持续400ms）
- **触觉反馈**：触发设备短振动（vibration pattern: 100ms），提醒用户匹配错误
- **听觉反馈**：播放低沉的"嗡"音效，与成功音效形成鲜明对比

[截图：匹配成功的粒子特效效果，卡牌消除位置出现彩色粒子爆炸]

[截图：匹配失败的抖动反馈效果，卡牌显示水平偏移的抖动状态]

#### 3.1.7 Combo连击系统

Combo连击系统通过递增奖励机制激励用户保持专注和准确：

- **连击定义**：连续匹配成功（中间无失败）的次数即为当前Combo数
- **视觉递进**：
  - Combo 3：屏幕边缘出现微弱泛光效果
  - Combo 5：泛光增强，颜色变为金色
  - Combo 8：全屏金色光环脉冲动画
  - Combo 10+：彩虹光环+屏幕轻微缩放脉冲
- **音调递进**：每次连击成功，消除音效的音调升高一个半音，形成听觉上的上升感
- **连击中断**：一旦匹配失败，Combo归零，视觉和音效恢复基础状态
- **连击记录**：每局游戏的最大Combo数记录到game_session表中，用于学习报告统计

### 3.3 学习计划引擎

学习计划引擎根据用户的学习目标和时间约束，智能生成每日学习计划，确保在规定时间内完成词库学习。

#### 3.3.1 输入参数

学习计划的生成依赖以下用户输入参数：

| 参数 | 类型 | 说明 | 示例 |
|------|------|------|------|
| 词库总量 | int | 所选词库的总单词数 | 3500 |
| 已掌握量 | int | 用户已标记为掌握的单词数 | 500 |
| 剩余天数 | int | 用户期望完成学习的天数 | 90 |
| 每日时长 | int | 用户每天可用于学习的时间（分钟） | 30 |

#### 3.3.2 每日新词量计算

系统根据以下公式计算每日新词学习量：

```
待学总量 = 词库总量 - 已掌握量
理论每日新词 = 待学总量 / 剩余天数
时长约束新词 = 每日时长 / 新词耗时系数

每日新词量 = min(理论每日新词, 时长约束新词)
```

其中，**新词耗时系数**为1.5分钟/词（即1分钟可处理约0.67个新词），**复习耗时系数**为0.33分钟/词（即1分钟可处理约3个复习词）。

**计算示例**：
- 待学总量 = 3500 - 500 = 3000词
- 理论每日新词 = 3000 / 90 ≈ 33词/天
- 时长约束新词 = 30 / 1.5 = 20词/天
- **每日新词量 = min(33, 20) = 20词/天**

#### 3.3.3 时长约束模型

每日学习时间分配遵循以下模型：

| 活动类型 | 耗时系数 | 说明 |
|---------|---------|------|
| 新词学习 | 1.5分钟/词 | 包含卡片浏览（15秒/词）和首次消除巩固 |
| 复习消除 | 0.33分钟/词 | 4×4网格约2分钟/局（8词），6×6网格约4分钟/局（18词） |
| 错词重练 | 0.5分钟/词 | 介于新词和复习之间 |

每日时间分配公式：
```
每日总时长 = (每日新词 × 1.5) + (每日复习词 × 0.33) + (每日错词 × 0.5)
```

系统确保每日总时长不超过用户设定的每日时长上限。

#### 3.3.4 复习债务管理

当累积的待复习单词超过每日可处理量时，形成"复习债务"。系统采用以下策略管理债务：

1. **债务上限**：每日最多安排200词的复习量，超出部分自动分摊至后续日期
2. **优先级排序**：复习单词按next_review_date升序排列，过期越久的单词优先复习
3. **债务分摊**：超出部分均匀分摊至未来7天内，避免单日负担过重
4. **债务告警**：当累计债务超过500词时，在首页显示告警提示，建议用户调整学习计划

[截图：学习计划设置界面，显示词库总量、已掌握量、剩余天数、每日时长四个输入项，底部显示计算后的每日新词量和预计完成日期]

### 3.4 SM-2间隔重复算法

SM-2算法是本软件科学记忆体系的核心，确保每个单词在最优时间点被复习，最大化记忆效率。

#### 3.4.1 算法概述

SM-2（SuperMemo Algorithm 2）由Piotr Woźniak于1987年提出，是间隔重复领域最经典、应用最广泛的算法。其核心思想是：根据用户对记忆项目的回忆质量评分，动态调整下次复习的间隔天数和难度因子，使复习节奏与遗忘曲线精确匹配。

本软件将SM-2算法与消除游戏深度结合，用游戏表现数据（匹配耗时、错误次数）自动计算质量评分，无需用户手动评分。

#### 3.4.2 质量评分（Q值）

质量评分Q取值范围为0-5，含义如下：

| Q值 | 含义 | 对应游戏表现 |
|-----|------|-------------|
| 0 | 完全不记得 | 连续3次匹配错误 |
| 1 | 有印象但完全想不起来 | 连续2次匹配错误，且首次匹配耗时>10秒 |
| 2 | 想起来但很困难 | 匹配错误1次后成功，且匹配耗时>8秒 |
| 3 | 想起来但有犹豫 | 首次匹配成功，但耗时5-8秒 |
| 4 | 毫不犹豫地想起来 | 首次匹配成功，耗时2-5秒 |
| 5 | 完美记忆 | 首次匹配成功，耗时<2秒 |

质量评分的计算逻辑封装在`Sm2Service.calculateQuality()`方法中，输入参数为匹配耗时（毫秒）和错误次数，输出Q值。

#### 3.4.3 复习间隔计算

根据Q值，SM-2算法按以下规则计算复习间隔：

**当 Q < 3（未通过）**：
- 间隔重置为0天（即下次复习为当天/次日）
- repetitions重置为0
- 单词重新进入学习队列

**当 Q >= 3（通过）**：
- repetitions递增1
- 间隔按以下规则计算：
  - repetitions = 1 → interval = 1天
  - repetitions = 2 → interval = 6天
  - repetitions >= 3 → interval = round(previous_interval × easiness_factor)

**间隔计算示例**（假设EF=2.5）：

| 复习次数 | Q值 | 间隔（天） | 说明 |
|---------|-----|-----------|------|
| 第1次 | 4 | 1 | 首次复习间隔1天 |
| 第2次 | 5 | 6 | 第二次复习间隔6天 |
| 第3次 | 4 | 15 | 6 × 2.5 = 15天 |
| 第4次 | 3 | 37 | 15 × 2.5 = 37.5 ≈ 38天 |
| 第5次 | 4 | 94 | 38 × 2.5 = 95天 |

#### 3.4.4 难度因子更新

难度因子（Easiness Factor, EF）反映单词的记忆难度，取值范围1.3~2.5+，默认初始值2.5。EF越大表示越容易记忆，间隔增长越快。

更新公式：
```
EF' = EF + (0.1 - (5 - Q) × (0.08 + (5 - Q) × 0.02))
```

**更新示例**：

| Q值 | EF变化 | 说明 |
|-----|--------|------|
| 5 | EF + 0.10 | 完美记忆，难度降低 |
| 4 | EF + 0.02 | 记忆良好，难度略降 |
| 3 | EF - 0.08 | 记忆勉强，难度增加 |
| 2 | EF - 0.20 | 记忆困难，难度显著增加 |
| 1 | EF - 0.34 | 几乎遗忘，难度大幅增加 |
| 0 | EF - 0.50 | 完全遗忘，难度剧增 |

**下限保护**：若计算后的EF' < 1.3，则强制设为1.3，确保间隔不会无限缩短。

#### 3.4.5 掌握判定

当单词的复习间隔超过21天时，系统判定该单词为"已掌握"（is_mastered = TRUE）。掌握判定逻辑如下：

```
if (interval_days >= 21 && repetitions >= 3) {
    is_mastered = true;
}
```

已掌握的单词不再出现在日常复习队列中，但用户可在"已掌握词库"中查看和手动重置。若用户主动重置某已掌握单词，则is_mastered恢复为FALSE，interval_days重置为0，重新进入复习循环。

### 3.6 错词本模块

错词本模块自动记录用户在消除游戏中匹配失败的单词，提供针对性的错词重练功能。

#### 3.6.1 自动记录机制

在消除游戏中，以下情况会触发错词记录：

- 匹配失败（选择了错误的英汉配对）：该单词的error_count加1
- 超时未匹配（卡牌翻开后超过10秒未选择配对）：该单词的timeout_count加1

错词记录存储在user_word_progress表中，通过last_quality字段（Q<3）和review_debt字段标识。

#### 3.6.2 错词重练

用户可在错词本页面选择"错词重练"，系统从错词列表中筛选出last_quality < 3的单词，生成专属消除游戏对局：

- 错词数量 ≤ 8：使用4×4网格
- 错词数量 > 8：使用6×6网格，优先选择error_count最高的18个单词

错词重练的游戏表现同样会更新SM-2进度数据，形成"犯错→重练→纠偏"的闭环。

#### 3.6.3 错词统计

| 统计项 | 说明 |

| 已纠正 | 曾经在错词本中但Q值已恢复到3以上的单词数量 |
| 高频错词 | error_count排名前10的单词列表 |

### 4.3 复习流程

```
    - 计算新的interval_days
    - 设置next_review_date
    - 检查是否达到掌握条件
    │
    ▼
返回首页，更新今日数据
```

## 5. 数据结构设计

本软件使用SQLite数据库进行本地数据持久化，通过drift ORM框架实现类型安全的数据访问。数据库名称为`wordmatch.db`，当前版本为1。

### 5.1 word 表（词库表）

word表存储所有词库的单词数据，是应用最基础的数据表。

| 字段名 | 数据类型 | 约束 | 说明 |
|--------|---------|------|------|
| id | TEXT | PRIMARY KEY | 单词唯一标识，格式为"{book_id}_{word}"，如"cet4_core_abandon" |
| word | TEXT | NOT NULL | 英文单词 |
| phonetic_us | TEXT | - | 美式音标，如"/əˈbændən/" |
| phonetic_uk | TEXT | - | 英式音标，如"/əˈbændən/" |
| definition | TEXT | NOT NULL | 中文释义，如"v. 放弃；抛弃" |
| example_sentence | TEXT | - | 例句，如"He abandoned his car in the snow." |
| frequency | INTEGER | DEFAULT 3 | 词频等级（1-5，1最常用，5最不常用） |
| book_id | TEXT | NOT NULL | 所属词库ID，关联词库表 |
| root_parts | TEXT | - | 词根拆分JSON，如'[{"part":"a","meaning":"远离"},{"part":"bandon","meaning":"控制"}]' |
| has_mnemonic | BOOLEAN | DEFAULT FALSE | 是否有记忆法 |

**索引设计**：
- `idx_word_book_id`：基于book_id的索引，加速按词库查询
- `idx_word_word`：基于word字段的索引，加速单词查找
- `idx_word_frequency`：基于frequency的索引，支持按词频排序

**数据量估算**：高考3500 + CET4 2500 + CET6 2000 + 考研5500 + IT 800 + 其他 ≈ 16000条记录（去重后约12000条）。

### 5.2 user_word_progress 表（用户单词进度表）

user_word_progress表存储每个用户对每个单词的学习进度数据，是SM-2算法的核心数据支撑。

| 字段名 | 数据类型 | 约束 | 说明 |
|--------|---------|------|------|
| id | INTEGER | PRIMARY KEY AUTOINCREMENT | 自增主键 |
| user_id | TEXT | NOT NULL DEFAULT 'local_user' | 用户ID，当前版本固定为'local_user' |
| word_id | TEXT | NOT NULL | 单词ID，关联word表id字段 |
| book_id | TEXT | NOT NULL | 所属词库ID |
| easiness_factor | REAL | DEFAULT 2.5 | SM-2难度因子，范围1.3~2.5+ |
| interval_days | INTEGER | DEFAULT 0 | 当前复习间隔天数 |
| repetitions | INTEGER | DEFAULT 0 | 连续成功复习次数 |
| next_review_date | TEXT | NOT NULL | 下次复习日期，格式"YYYY-MM-DD" |
| last_quality | INTEGER | DEFAULT 0 | 最近一次SM-2质量评分（0-5） |
| is_mastered | BOOLEAN | DEFAULT FALSE | 是否已掌握（interval >= 21天且repetitions >= 3） |
| review_debt | INTEGER | DEFAULT 0 | 复习债务（逾期未复习的天数） |

**索引设计**：
- `idx_progress_user_book`：基于(user_id, book_id)的复合索引，加速按用户和词库查询
- `idx_progress_next_review`：基于(user_id, next_review_date)的复合索引，加速SM-2筛选
- `idx_progress_mastered`：基于(user_id, is_mastered)的复合索引，加速掌握统计
- `idx_progress_quality`：基于(user_id, last_quality)的复合索引，加速错词本筛选

**唯一约束**：UNIQUE(user_id, word_id, book_id)，确保同一用户在同一词库中对同一单词只有一条进度记录。

**数据量估算**：假设用户学习2个词库，每个词库3500词，则约7000条记录。

### 5.3 game_session 表（游戏对局记录）

game_session表记录每次消除游戏对局的详细数据，用于学习报告和统计分析。

| 字段名 | 数据类型 | 约束 | 说明 |
|--------|---------|------|------|
| id | INTEGER | PRIMARY KEY AUTOINCREMENT | 自增主键 |
| book_id | TEXT | NOT NULL | 对局使用的词库ID |
| grid_size | TEXT | NOT NULL | 网格规格，"4x4"或"6x6" |
| words_played | TEXT | NOT NULL | 本局涉及的单词ID列表，JSON数组格式 |
| correct_count | INTEGER | DEFAULT 0 | 正确匹配次数 |
| wrong_count | INTEGER | DEFAULT 0 | 错误匹配次数 |
| combo_max | INTEGER | DEFAULT 0 | 本局最高连击数 |
| duration_seconds | INTEGER | - | 对局时长（秒） |
| completed_at | TEXT | - | 对局完成时间，ISO 8601格式 |

**索引设计**：
- `idx_session_book`：基于book_id的索引，加速按词库统计
- `idx_session_completed`：基于completed_at的索引，加速按日期查询
- `idx_session_book_date`：基于(book_id, completed_at)的复合索引，加速按词库和日期范围统计

**数据量估算**：假设用户每天进行5局游戏，使用300天，则约1500条记录。

```
│ root_parts      │       │ last_quality             │

└─────────────────┘       │ review_debt              │
                          └──────────────────────────┘
```

### 6.2 外部服务接口

#### 6.2.1 有道词典TTS API

用于单词发音功能，将文本转换为语音播放。

| 项目 | 说明 |
|------|------|
| 接口地址 | https://openapi.youdao.com/ttsapi |
| 请求方式 | GET |
| 认证方式 | 应用ID + 签名 |

**请求参数**：

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| appKey | String | 是 | 应用ID |
| q | String | 是 | 要朗读的文本（英文单词） |
| langType | String | 是 | 语言类型，英语为"en" |
| signType | String | 是 | 签名类型，固定为"v2" |
| salt | String | 是 | 随机字符串 |
| sign | String | 是 | 签名（appKey + q + salt + appSecret的MD5） |

**响应**：返回音频流（MP3格式），由audioplayers库播放。

#### 6.2.2 AI大模型API

用于词库智能清洗功能，调用兼容OpenAI API格式的大语言模型服务。

| 项目 | 说明 |
|------|------|
| 接口地址 | 用户自定义（在设置中配置） |
| 请求方式 | POST |
| 认证方式 | Bearer Token（用户配置的API Key） |

**请求体**：

```json
{
  "model": "gpt-3.5-turbo",
  "messages": [
    {
      "role": "system",
      "content": "你是一个英语词汇专家。请从用户提供的文本中提取所有英语单词，去除重复，并为每个单词提供中文释义和一个例句。以JSON数组格式返回。"
    },
    {
      "role": "user",
      "content": "用户粘贴的原始文本内容"
    }
  ],
  "temperature": 0.3
}
```

**响应体**：

```json
{
  "choices": [
    {
      "message": {
        "content": "[{\"word\":\"abandon\",\"definition\":\"v. 放弃；抛弃\",\"example\":\"He abandoned his plan.\"}]"
      }
    }
  ]
}
```

**安全说明**：
- API地址和密钥由用户自行配置，存储在本地设备
- 本应用不收集、不中转、不存储任何API密钥或用户文本数据
- 所有网络请求均使用HTTPS加密传输
- 用户可随时在设置中清除API配置信息

## 附录B：状态管理架构

本软件采用Riverpod进行状态管理，核心Provider定义如下：

| Provider名称 | 类型 | 说明 |
|-------------|------|------|
| wordRepositoryProvider | Provider\<WordRepository\> | 词库数据仓储实例 |
| progressRepositoryProvider | Provider\<ProgressRepository\> | 学习进度仓储实例 |
| sm2ServiceProvider | Provider\<Sm2Service\> | SM-2算法服务实例 |
| gameServiceProvider | Provider\<GameService\> | 游戏服务实例 |
| currentThemeProvider | StateNotifierProvider | 当前主题状态 |
| todayStatsProvider | FutureProvider\<DailyStats\> | 今日学习统计数据 |
| dueReviewsProvider | FutureProvider\<List\<UserWordProgress\>\> | 待复习单词列表 |
| studyPlanProvider | StateNotifierProvider | 学习计划状态 |
| gameSessionProvider | StateNotifierProvider | 当前游戏对局状态 |

所有Provider通过Riverpod的依赖注入机制管理生命周期，UI层通过`ref.watch()`监听状态变化并自动重建，实现响应式的数据驱动UI更新。
